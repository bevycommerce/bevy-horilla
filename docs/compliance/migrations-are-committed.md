# Migrations are committed

A model change ships its generated migration in the **same pull request**. The staging boot runs
`migrate`; nothing on any server generates migrations. A model change merged without one leaves the
database without the column and surfaces as a runtime error for whoever opens that screen next — and
for everyone else whose local database diverges.

This repository has been bitten by exactly this before: migrations were being generated at runtime
on a server instead of committed, which drifted the schema silently until a column was missing on
someone else's database.

How-to: [`DEVELOPER_GUIDE` — Migrations](../DEVELOPER_GUIDE.md#migrations).

## Do

- Run `python manage.py makemigrations <app_label>` locally and commit the generated file with the
  model change.
- Run `python manage.py makemigrations --check --dry-run` before opening the PR. It exits non-zero
  when a model change has no migration. `migrate` cannot detect this (it succeeds against whatever
  is committed) and neither can `manage.py check`.
- Read the generated migration before committing it. You may rename the file to describe the change
  when the autogenerated name is noise — but **only if nothing references it yet.** A migration's
  name is its identity in the graph: if another migration already lists it in `dependencies`, or
  a `run_before` points at it, rename both sides in the same commit, or leave the name alone.
  Django cannot load a graph with a dangling dependency. Keep the number either way.
- Say in the PR description that the PR adds a migration, and what it does to existing rows.
- Make a data migration reversible, or state in its docstring why it cannot be.
- Add a new migration to fix a mistake in one that has already run on staging.

## Do not

- Run `makemigrations` **anywhere but your own machine** — not on a server, not by SSH, not in a
  container shell, not from a script. Generating a migration on a server is what drifted the schema
  before.
- Run `migrate` **by hand** on a server, by SSH or in a container shell. The container entrypoint
  applies migrations on boot, and that automated step is the only thing that should run them there
  ([`reference/ENVIRONMENTS.md`](../reference/ENVIRONMENTS.md)). Running it yourself races the deploy
  and applies whatever is in that checkout, which is not necessarily what merged.
- Remove or bypass the boot `migrate` to satisfy the two rules above. It is the documented deploy
  step, not a violation of them.
- Edit or delete a migration that has already been applied on staging or production.
- Commit a model change with "migration to follow" in the description.
- Reformat a migration. `migrations/` is excluded from `black`, `isort`, `ruff` and the whitespace
  hooks for a reason — leave the files as Django generated them.
- Squash existing migrations as part of another change.
